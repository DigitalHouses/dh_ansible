# Обязательные правила для людей, AI-агентов и coder-исполнителей

Прочитать `docs/engineering-principles.md`, `docs/scope.md`, `docs/architecture.md` и связанные ADR **до** изменения кода. Эти правила распространяются на все новые роли, модули, playbooks, тесты и operator workflows.

**Правило нового развёртывания (02.11.2026):** для чистого site runner использовать **только** стандартный [`bootstrap/install.sh`](bootstrap/install.sh), команда опубликована в [README](README.md#единая-точка-входа--tiny-bootstrap). Удаление CT/VM — отдельная ручная операция PVE при адресном разрешении, **никогда внутри Bootstrap или обёртки «replace + install»**. Установщик при занятом CT1231 обязан завершиться `BLOCKED` без изменений. Прежний `bootstrap/replace-site-runner.sh` удалён после инцидента `pct stop --timeout 60` (`Unknown option: timeout` на PVE 8.4). Ставится `2.20.16-beta9` из pinned SHA256, без миграции старой Semaphore DB или credentials. Живой E2E этой версии пока не принят.

**Tiny Bootstrap — Fresh E2E ACCEPTED 31.10.2026:** [docs/architecture.md](docs/architecture.md) — **ровно четыре этапа**: стандартный Debian 13 LXC через `pct` на PVE → публичный pinned Git checkout внутри LXC → гостевой установщик Ansible + Semaphore → **ровно задача №00**. На PVE Ansible не устанавливается. Bootstrap **не** загружает private Fleet, не создаёт PVE identities, не устанавливает Media workers и не вызывает задачи 10–90; это зона отдельно разрешённых задач Semaphore. После установки пользователь вручную запускает №00 через Semaphore. Не возвращать старый Python orchestrator. Fresh E2E **успешно принят**: `RESULT_RC=0`, `TASK_00_ONLY=PASS`, затем №00 через Semaphore создала десять шаблонов, сохранила себя и завершилась без ошибок. [Отчёт приёмки](docs/acceptance/tiny-bootstrap-2026-10-31.md). **Адресное разрешение на уничтожение CT1231 от 31.10.2026 использовано для нового Fresh E2E** (№05/06 приняты). Существующий runner повторно не удалять без отдельного нового явного разрешения, проверки PVE/CT/rootfs и защиты других гостей; сам Bootstrap никогда не удаляет guests. PVE/Fleet/Media workers не приняты этим тестом.

## Credentials — принятое целевое решение ADR-0021

**Реализация 02.11.2026: draft PR #101.** После чистого Bootstrap Semaphore 2.20.16-beta9 в CT1231 доступна только №00. В `main` пока прежние №05/06; новый код PR — `playbooks/obtain-site-credentials.yml` (нативный `ansible.builtin.uri`, секреты в существующей Variable Group `Empty`) и `playbooks/check-site-credentials.yml` (PVE root@pam HTTPS + `/nodes`). Python-клиент №05 удалён. В установленном root-owned seeder форма №05 **обязательно** `target=env`, хотя сохраняемые Secrets — `type=var`; `target=var` формы требует новой принятой ревизии Bootstrap. **Не объявлять №05/06 live-ready до мержа, синтаксической и реальной UI приёмки**. №07 и общий preflight пока не реализованы. Операторский документ: [credential-setup](docs/runbooks/credential-setup.md).

**Новый обязательный контракт:** [ADR-0021 — native Semaphore OSS credentials](docs/decisions/0021-semaphore-native-credentials.md). В каждом объекте одна задача **№05 Obtain Credentials** вводит все credentials через Secret Survey и сохраняет их в **штатном Key Store и Variable Groups → Secrets самого Semaphore**. **№06 Check Credentials** проверяет весь обязательный набор объекта, агрегирует все ошибки с конкретными действиями по исправлению. Любая обычная задача вызывает свежую общую проверку перед изменениями; при `BLOCKED` не запускается. Никаких дополнительных файловых secret stores, платных компонентов и самодельной базы. Зашифрованная БД Semaphore и отдельно сохранённый ключ шифрования должны иметь проверяемое резервное восстановление.

**Повтор №05 и новый site Git:** все поля Secret Survey допускают пропуск; незаполненное поле оставляет ранее сохранённый credential без изменений. Администратор может повторить №05 и заменить только один неверный пароль; сохранённые значения не подставлять обратно в форму. **№05 не создаёт репозиторий** — только сохраняет все введённые credentials в Semaphore. **№06** проверяет весь обязательный набор, включая GitHub; **№07** после успешной свежей проверки создаёт приватный site repository либо безопасно проверяет/adopt существующий без перезаписи. Создание требует временного разрешения GitHub, которое не оставлять на домашнем runner; дальнейший доступ — read-only только к своему repo. Bootstrap по-прежнему создаёт лишь №00. Подробности и отрицательные тесты — [ADR-0021](docs/decisions/0021-semaphore-native-credentials.md).

**Единый доверенный административный контур:** Semaphore и Ansible в выделенном LXC одного site имеют одинаковый уровень доверия и право штатным API управлять Key Store/Variable Groups **своего** проекта. Не создавать per-task privilege broker, root worker или отдельную систему хранения для №05. Это намеренно широкие полномочия всех доверенных playbooks конкретного объекта; между разными объектами полномочия не общие. Для PVE/Linux managed hosts действуют отдельные SSH/`become` identities. Подробности — [ADR-0021](docs/decisions/0021-semaphore-native-credentials.md).

**Внимание:** старые описания №05 GitHub / №06 Fleet Vault и прототип `site_vault_v1` ниже — историческое/переходное состояние кода, **не целевая архитектура**. Нельзя объявлять внедрение ADR-0021 без реализованного и принятого E2E. Миграция — без потери существующих credentials.

## Отраслевые практики имеют приоритет над нашими решениями

**Обязательное правило для всех разработчиков и AI-агентов: industry best practices first.** Перед проектированием или исправлением инфраструктуры сначала проверить актуальную официальную документацию применяемых продуктов и общепринятые практики; затем искать поддерживаемые встроенные механизмы и существующие решения. Не создавать собственный стандарт, протокол, credential provider, worker, DSL или замену штатному инструменту лишь потому, что это кажется удобнее. Наши документы **не заменяют и не переопределяют** внешние стандарты безопасности, совместимости и эксплуатации.

Когда штатное решение не покрывает проверенную потребность, исключение оформлять явно: ссылкой на источник/версию, описание ограничения, оценкой риска и сопровождения, обоснованием минимальной собственной реализации, проверками и условиями отказа от неё. Требования конкретного объекта (имена, параметры, желаемое состояние) разрешены как **site policy**, но не выдаются за отраслевые best practices. Если имеются противоречия между существующими правилами проекта и официальными рекомендациями, **остановить изменение и предложить исправление правила**, не добавлять обходной механизм.

Нормативный принцип: [P00 — Industry standards first](docs/engineering-principles.md).

## ПЕРВОЕ ДЕЙСТВИЕ AI-агента: запуск/обновление/диагностика инфраструктуры

**Обязательно прочитать [Единый операционный runbook для AI-агентов](docs/runbooks/ai-agent-execution.md) до любой инфраструктурной операции**, до фразы «я не могу запустить» и до попытки запуска. В нём зафиксированы: Remote Desktop Commander, пользователь `semaphore`, прямой запуск Ansible без Semaphore API, публикация pinned release защищённого worker, preflight, approval, независимый acceptance и STOP при security-deny.

**Стандартный запуск задач после №00 — через Semaphore.** Дополнительный инженерный запуск через root-owned pinned `scripts/dh-task-runner.py` возможен **только после его отдельной разрешённой установки** по [runbook](docs/runbooks/ai-agent-execution.md): `PLAN_ONLY` по умолчанию, `--execute` после разрешения. На принятом Tiny Bootstrap runner launcher, protected PVE workers и административный доступ Ansible к guest **не устанавливались**. Новый общий стандарт установки ПО — [ADR-0020](docs/decisions/0020-infrastructure-privilege-and-software-installation.md): штатные Ansible roles с `become` после отдельного site/target commissioning, а не обработчики для каждой задачи. №00 не выдаёт root-прав. Ни №81, ни новые задачи не требуют отдельного AI-launcher. Security-deny подключённого инструмента не обходить.

**Не искать процедуру в истории чатов и не создавать альтернативный исполнитель.** История — только свидетельство, а актуальная инструкция — единственный нормативный источник. Для специфики медиасервера после неё читать [media runbook](docs/runbooks/media-semaphore-launch.md). Не дублировать команды запуска в верхних документах.

**Матрица полномочий всех задач:** [реестр targets/credentials/operations](docs/standards/task-privilege-matrix.md). **Общий onboarding административного доступа:** [runbook per-target infrastructure credentials](docs/runbooks/infrastructure-access-commissioning.md). Каждая новая или изменяемая задача обязана указывать, каким Linux/API principal и с какими разрешениями она работает. Нельзя выдавать произвольный root доступ через копирование per-task worker.

**Задача №40 и общий доступ к установке ПО:** сначала читать [ADR-0020](docs/decisions/0020-infrastructure-privilege-and-software-installation.md) и [runbook Remote Desktop Commander](docs/runbooks/remote-commander-commissioning.md). Для всех software/service задач использовать `infrastructure_access` и штатное `become` с авторизованными target credentials. При отсутствующем административном доступе `BLOCKED`, а не создание временного root-worker. Сервис active сам по себе не означает Online: проверить pairing и подключение.

**Новые sites — отдельный Ansible Vault:** Fresh Bootstrap создаёт `site.credentials_profile=site_vault_v1`; до первого выполнения №06 в private Fleet должен существовать зашифрованный `secrets/sites/<site-id>.vault.yml`, с собственным паролем владельца. №06 проверяет точный `site_id` и сохраняет рабочую копию пароля `0600` только для данного runner. **Общий Fleet master password разрешён только как legacy-компатибильность для уже работающих объектов.** Нет Vault своего site — `BLOCKED`, не переходить к чужому Vault и не создавать секреты в открытом виде. Обязательная инструкция: [site-credentials-onboarding.md](docs/runbooks/site-credentials-onboarding.md). SSH host access — штатный `become` и per-target identities, а не per-task workers.

**Первичная авторизация Fleet — только после №00:** задача `05-Получить credentials GitHub` показывает одноразовый device code; задача `06-Ввести master password Fleet Vault` принимает одно скрытое значение и сохраняет его локально на runner. [Операторский runbook №05/06](docs/runbooks/credential-setup.md). **Fresh E2E №00→№05→№06 принят 31.10.2026** на Jonsbo CT1231: GitHub Device Flow, private Fleet checkout, успешная расшифровка Vault и сохранение пароля `0600` подтверждены журналами. [Отчёт](docs/acceptance/fleet-credentials-2026-10-31.md). Reboot и downstream задачи 10–90 этим тестом не приняты. Никакого нового Credentials Provider, Vault master password в Bootstrap или автоматической установки PVE workers. Тестируем только через свежую установку из закреплённого Git SHA; **ручные замены seeder и hotfix в LXC запрещены**. Операционная последовательность — [runbook](docs/runbooks/credential-setup.md).

**Глобальный Credential Readiness Gate:** любое штатное Deploy/Update/Configure Ansible-задание перед изменениями проверяет весь утверждённый обязательный набор credentials своего объекта (включая не связанные непосредственно с задачей). Это сознательная строгая policy владельца, а не универсальная практика Ansible. Проверка **собирает все ошибки**, возвращает диагностический список с причиной/исправлением и итог READY/BLOCKED; на BLOCKED никаких изменений. Только Bootstrap, Obtain Credentials, Check Credentials и санкционированное recovery допускаются без READY. История Semaphore не заменяет свежий preflight. Нормативный контракт: [Site Credential Readiness Gate](docs/runbooks/site-credentials-onboarding.md#обязательный-глобальный-credential-readiness-gate).

## Non-negotiable

1. **Не создавать сценарий под атомарную операцию или конкретную identity.** В частности, запрещены отдельные writers/preflight/verify-скрипты для `ha_user`, `pve_user`, `torrent_user`, отдельного dataset, share или snapshot при наличии одной общей операции. Один тип ресурса — один переиспользуемый контракт; список экземпляров — только в inventory.
2. До написания нового кода искать существующую роль/модуль. Дублирующую и конкурирующую реализацию не добавлять. Исключения для аппаратного bootstrap/recovery должны быть обоснованы в PR или ADR.
3. Не добавлять зависимости от устаревших репозиториев. Архивные реализации не являются рабочим источником кода. Изменения на чужих production-узлах исключены без отдельного разрешения владельца.
4. Читать live-state перед планом, применять **только утверждённые** различия, независимо проверять postconditions. При неопределённом результате write API прекращать записи и повторять **только read-only наблюдение**.
5. Параметры сайта — в `inventories/<site>/`, не в коде роли. Один **общий кодовый** repository обслуживает весь fleet; отдельные **приватные site repositories с inventory/config** разрешены согласно ADR-0021. Копии общих roles/playbooks по домам запрещены. Отсутствие ресурса в желаемом списке само по себе не разрешает удаление.
6. Реальные опасные операции (удаление, wipe, reset/recursive ACL, PCI/SATA, изменение сети доступа) требуют адресного разрешения, preconditions и recovery plan. `--check` не считать полноценным dry-run.
7. SSH с verified host keys для обычного Linux; поддерживаемые API и проверка TLS/идентичности для PVE, TrueNAS и appliances. Минимально необходимые права, Vault и `no_log` для секретов, никакого plaintext в Git/логах/CLI args.
8. Git commit идентифицирует конкретную версию плана и применения; CI до apply. Не утверждать `PASS` по успешному запуску команды: нужны независимые фактические postconditions и повторный запуск `changed=0`.
9. Код, имена ключей, объектов и тестов — на английском. Документация, операторские инструкции и отчёты — на русском. Не создавать лишних инфраструктурных зависимостей.
10. При признаках чрезмерной сложности, дублирования или неверного паттерна **остановить реализацию, сообщить владельцу и предложить исправление**, а не увеличивать число скриптов и проверок.
11. **Bonjour/mDNS обязателен для всех новых сетевых VM/LXC, создаваемых Ansible на любом объекте.** Каждая роль provisioning обязана включать переиспользуемый guest-network baseline и проверять публикацию уникального `<hostname>.local` самим гостем. Для Linux без штатного mDNS — `avahi-daemon` (enabled/active); для ОС со встроенным механизмом — только штатный стек, без второго daemon. Доступ UDP/5353 ограничен локальным интерфейсом/сегментом LAN; DNS-SD объявляет лишь реально доступные сервисы. Независимый verify — разрешение имени с другого устройства этой LAN в фактический IP гостя; повторный apply `changed=0`. Без успешного verify сетевой guest provisioning не принимать. Явные технические исключения — только в per-site inventory с причиной; существующие production-гости не изменять массово без отдельного audit/plan/approval. Полный контракт: `docs/standards/guest-network-mdns.md`.
12. **Все новые управляемые ZFS-пулы именовать строго `<owner>-pool`.** `owner` берётся из `site.owner_slug` в Fleet SoT, а не из `site.id` и не из названия VM/CT/объекта. Имя пула, datasets и пути не должны собираться из site slug. Уже существующие legacy-пулы не переименовывать при `keep + import`: обнаруживать и сохранять их фактические имена, GUID и данные. Любое переименование — отдельный согласованный audit → plan → apply → verify с recovery plan. При несовместимой валидации — `BLOCKED`, не обходить проверки. Стандарт: `docs/standards/storage-pool-naming.md`.

## Разрешённая область текущего этапа

Пилот bootstrap выполняется на выделенном локальном runner. Production-объекты не меняются в ходе переноса репозиториев. Любые операции с TrueNAS ACL/shares и переключение ownership требуют отдельного plan/apply и явного разрешения.


## Работа в терминале оператора

Давать один проверяемый блок за этап. Не завершать и не заменять интерактивный shell оператора; при необходимости использовать subshell. Завершать отчёт строками `DONE` и `TERMINAL STAYS OPEN`. Bash/Python допустимы по назначению, но не как замена idempotent Ansible-модулей.
