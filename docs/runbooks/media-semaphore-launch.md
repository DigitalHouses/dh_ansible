# Media Server: запуск Semaphore и прямой инженерный fallback

> **АКТУАЛЬНО · 03.11.2026 · №80:** владелец выбирает только действия `create / keep / recreate` и `erase / import`. Диск не выбирается по производителю, WWN, serial, старым PARTUUID или GUID. Целевое устройство — **единственный диск выделенного SATA-контроллера**, переданного Media VM через PCI Passthrough.
>
> На PVE preflight проверяет управляемую VM и PCI SATA-контроллер, но не ищет HDD через `/dev/disk/by-id` на самом PVE (после PCI passthrough диск хосту недоступен). В Media VM через PCI sysfs class `0x0106` и vendor/device этого контроллера обнаруживаются физические диски: **0 → `SATA_NO_DISKS`**, **2+ → `SATA_MULTIPLE_DISKS`**, **ровно 1 → продолжить**. Системный диск исключается.
>
> Выбор действия в Semaphore уже является распоряжением владельца: `approvals.provision/gpu_cutover/sata_cutover` не должны становиться вторым разрешением. Проверки защищают конкретные ресурсы, но не переоценивают намерение оператора.
>
> **`erase`** без оглядки на прежнюю разметку/NTFS/ZFS полностью уничтожает данные на единственном SATA-диске и создаёт `<owner>-pool`. Повторного подтверждения в задаче нет: выбор `erase` — явное распоряжение. **`import`** подключает существующий ZFS-пул с того же диска без стирания и без автоматического перехода к `erase`. При замене единственного диска следующий явный `erase` сотрёт новый диск — сознательная controller-scoped политика. Другие VM, NVMe и SATA-контроллеры не затрагиваются.
>
> Реальное стирание производится исключительно внутри Media VM; boot importer допускает только `import`. CI и ревью не заменяют LIVE E2E №80 → №81.

**Обязательная точка входа для AI:** [Единый операционный runbook](ai-agent-execution.md). Только эта редакция правил №80 применяется к новым запускам; исторические записи ниже описывают старые инциденты.

**Область:** задача `80-Медиасервер · Развёртывание`, runner Ansible/Semaphore и штатный root SSH к PVE. Старый NFS backup export — только условная совместимость при наличии `backup_export` в site manifest; он не является обязательным условием выполнения №80 и будет выведен после миграции на PBS.
**Правила:** [AGENTS.md](../../AGENTS.md), [стандарт Semaphore](../standards/semaphore-task-design.md), [инженерные принципы](../engineering-principles.md).
**Статус:** новая controller-scoped реализация, live E2E ожидает проверки.

несуществующая команда `pvesm config local`. Корректная конфигурация

`pvesm set local --content ...`. Новый helper сначала независимо
читает/проверяет local dir storage и сохраняет все действующие
типы содержимого, добавляя только `snippets` по необходимости.

При сбое может остаться **остановленная, частично созданная VM2232**
с `scsi0` или `unused0`, но без законченной настройки Cloud-Init/PCI.
Режим `keep` допускает возобновление **только** этого управляемого
состояния: проверяются VMID, имя, DigitalHouses description, состояние
`stopped`, отсутствие lock, тип аппаратной VM, единственный system
volume `local-lvm:vm-<vmid>-disk-*`, заданные PCI devices и отсутствие
посторонних томов. Ветка `create` по-прежнему требует отсутствия VM.

**Без live readback нельзя утверждать**, что VM2232 присутствует,
каково состояние системного тома и какие сервисы Proxmox работают.
Стирание SATA HDD в Task #12 не наступило. Перед следующим запуском
всегда read-only `qm status/config` и общий PVE health audit;
не удалять VM или USB/SATA данные для «лечения» падения PVE helper.
После подтверждения наличия управляемой VM применять `keep`;
выбор `erase` уничтожит содержимое единственного HDD на SATA
контроллере при достижении guest storage этапа.

## QEMU Guest Agent · Fresh Bootstrap recovery · 03.11.2026

Реальный №80 Task #11: `create + erase` успешно создала/запустила
управляемую VM2232, но остановилась до доступа к физическому диску на
`qm guest exec 2232 -- /bin/cat /etc/ssh/ssh_host_ed25519_key.pub`
с `QEMU guest agent is not running` (60 попыток). Debian 13 official
cloud images **не включают** `qemu-guest-agent`; старая №80 ошибочно
пыталась прочитать ключ через него раньше установки пакета в гостевой роли.

**Исправление:** `bootstrap/dh-pve-media-deploy.py` готовит минимальные
Cloud-Init `vendor` (установка/запуск `qemu-guest-agent`) и стабильные
`meta` (instance-id) в `local:snippets` до первой загрузки.
Стандартные автоматически генерируемые PVE `user` (пользователь
`debian`, авторизованный SSH public key) и `network` не заменяются.
При установленном агенте сценарий `keep` не изменяет VM и не перезапускает её.

**Продолжение частично созданной VM2232:** один запуск **`keep + erase`**
после публикации фикса: проверка, что VM наша и физический SATA PCI
контроллер совпадает; если QGA отсутствует и штатные Cloud-Init snippets
ещё не заданы — добавление `vendor + meta`, один контролируемый
ACPI shutdown/start *только* VM2232, затем обычный QGA readback SSH key.
Если snippets уже заданы, перезапуск повторно не производится, чтобы
не прервать установку пакетов. Никакого ручного изменения VM, удаления
VM2232, ослабления SSH host key trust или замены credentials.

**Опасность:** при достижении шага ZFS действие `keep + erase`
стирает содержимое **единственного диска выделенного SATA-контроллера**.
Пока Task #11 остановилась на QGA, ZFS на этом HDD ею не стирался.

## №80 · Native Ansible · controller-scoped ZFS (03.11.2026)

- `playbooks/plan-pve-media-vm.yml`: берёт актуальный site inventory из приватного `site-<site.id>`, сверяет маркер и PVE root SSH. VM action и disk action независимы. Защита чужих VM/CT остаётся.
- `scripts/dh-media-pve-preflight.py`: проверяет SATA-контроллер и VM по PVE, без поиска HDD/WWN на хосте.
- `roles/media_guest_setup/files/dh-media-storage.py`: внутри VM находит физические диски именно на переданном SATA-контроллере по sysfs PCI ancestor class и vendor/device, измеренным на PVE. Ноль/много дисков — BLOCKED.
- `erase`: удаляет любую старую файловую систему и ZFS на этом единственном диске, создаёт `<owner>-pool`; не требует старый NTFS label, PARTUUID, serial, WWN или ZFS GUID. Активный multidisk pool/системный диск исключены.
- `import`: ищет ZFS только на выбранном диске и его разделах с `zpool import -d <device>`; при известном hostid-предупреждении для единственного ONLINE-пула допускает `-f`. Никогда не стирает.
- `dh-media-zfs-mount.sh.j2`: при старте гостя запускает ZFS reconciler строго с `--action import`.

**Все сочетания допустимы:** `create+erase`, `create+import`, `recreate+erase`, `recreate+import`, `keep+erase`, `keep+import`. Для обслуживания без потери данных обычно `keep+import`; явный `erase` повторно уничтожает содержимое даже уже созданного `<owner>-pool`.

**Приёмка:** после публикации кода провести живой №80, сверить `MEDIA_SATA_DISKS_FOUND=1`, `MEDIA_DISK_ACTION=ERASE/IMPORT`, `MEDIA_STORAGE_RECONCILED=PASS` и исполнить отдельную №81.

## Контракт реализации и диагностика

- Один шаблон Semaphore №80 — `playbooks/plan-pve-media-vm.yml`, два обязательных survey-параметра.
- PVE: `infrastructure_access`, штатный root SSH, проверенный PCI SATA-controller; без старого привилегированного watcher/worker.
- Media VM: PCI-контроллер идентифицируется vendor/device, HDD — только из гостя через SATA sysfs. 0,1,2+ дисков распознаются явно.
- Диск: `erase` уничтожает прошлое содержимое единственного диска, `import` только импортирует. Результат контролируется `MEDIA_STORAGE_RECONCILED=PASS`.
- №81: самостоятельная read-only приёмка сервисов после развёртывания. Никакие credentials в публичные логи не выводить.

## Частные ошибки, зафиксированные в E2E

- `ENABLED_BACKUP_TARGET_OFFLINE`: удалённая media VM предоставляла PVE NFS backup storage. Устранять точечным планом обслуживания и не игнорировать наличие активного `vzdump`. Временно отключённый job **обязательно восстановить после NFS acceptance**.
- `MEDIA_PLEX_PREFERENCES_FORMAT_DRIFT`: реальный корневой элемент Plex `Preferences.xml` называется `Preferences`, не `PlexMediaServer`. Исправлять исходный код и тесты в Git; для уже созданной VM выбирать `keep + import`, а не заново стирать диск.
- После `erase` у нового ZFS-пула будет новый GUID. **Обновлять pinned `import_pool_guid` для следующего `keep + import` не нужно:** импорт проверяет имя пула и единственный физический SATA-диск.

## Prowlarr: рабочая служба ещё не означает готовый поиск

После `create + erase` пароль владельца `serzhan` генерируется **заново** (не тот, что был до очистки ZFS). Файл `/serzhan-pool/digitalhouses/credentials/serzhan.txt` доступен только root/группе администраторов; **не печатать его содержание в автоматических логах, коммитах или ответах помощника**. Официальный bootstrap `dh-media-arr-auth` создаёт формы авторизации с этим владельцем в Radarr/Sonarr/Prowlarr и пишет owner-stamp на ZFS. Ранее сохранённые клиентом пароли после erase не должны считаться действительными. При жалобе на вход сначала проверить `Auth-Failure` в журнале Prowlarr и имя пользователя, затем помочь владельцу безопасно посмотреть свой актуальный паспорт *локально*.

`dh-media-arr-wire.py` соединяет Prowlarr с Radarr/Sonarr и qBittorrent, но **намеренно не добавляет сторонние индексаторы и cookies**. `Indexers=0` означает отсутствие поиска даже при корректных HTTP, процессах и API-связях. После удаления ZFS прежние настройки и cookies индексатора теряются, если они не хранились в отдельном подтверждённом источнике. Индексатор надо согласовать с владельцем, настроить допустимые реквизиты и проверить индексатор отдельно; не печатать приватные cookies.

Acceptance №81 выводит `prowlarr_indexers_present RESULT=SKIP DETAIL=NO_ENABLED_INDEXERS_OWNER_SELECTION_REQUIRED` при нуле источников; `PASS` по web/service **не** является поисковым E2E. Для поиска требуется отдельно проверить реальный запрос к индексатору, синхронизацию с Radarr/Sonarr и результаты, без обязательного скачивания защищённых авторским правом материалов.

## Обновления приложений и постеры Plex: регрессия после 30.10.2026

- Задача №80 (`keep + import`) разворачивает Radarr, Sonarr, Prowlarr с индивидуальными непривилегированными пользователями. Каталоги `/opt/Radarr`, `/opt/Sonarr`, `/opt/Prowlarr` должны принадлежать **только соответствующим сервисным пользователям** и оставаться доступными на запись собственному updater. **Не** выдавать `media_group` право изменения бинарников и **не** менять владельца `/opt` в целом. Unit `media-arr.service.j2` содержит `KillMode=process`, чтобы штатный обновлятор смог завершить дочерний процесс.
- Установка из `media_arr_releases` использует закреплённые архивы с SHA256 для первого деплоя; обновлённый встроенным updater бинарник **не** должен переписываться при повторном `keep + import` (у `unarchive` есть `creates`). Обновление приложения проверять фактической версией, доступностью HTTP, сохранением пользовательских indexers/queues и стабильностью после рестарта, а не только исчезновением предупреждения.
- Plex: сканирование обнаруживает добавленные файлы и должно запустить matching/metadata для новых объектов. Для **уже добавленных** фильмов без постеров необходимо отдельно выполнить `Refresh Metadata` и проверить агент, сопоставление и сетевые ошибки; бесконечное повторное сканирование или установка нового таймера не решают проблему. Поиск причины начинать с read-only статуса Plex, metadata matching и логов, **не** удалять каталоги/БД/кеш Plex и не менять токены.
- Acceptance №81 проверяет `native_update_writable_radarr|sonarr|prowlarr` и `plex_movie_posters` (сведения о matching и наличии poster metadata, без чтения/вывода токенов и имён файлов). Полностью загруженные постеры на клиенте, автоматическое восстановление постеров и успешное применение реального обновления **требуют отдельной live-проверки**, поскольку наличие URL метаданных в БД не гарантирует успешную загрузку изображения.
- После изменения №80 синхронизировать код через штатный Git checkout Semaphore и проверять фактический commit в журнале. Старого release protected worker у native №80 нет. Для устранения ошибок приложения не выбирать destructive action; штатный путь — `keep + import` и №81.

## Filestash: ошибка `unpacking idp - invalid character` (30.10.2026)

- Реальный симптом: `http://<media-vm>:8334/` отвечает HTTP 200, но `/api/session/auth/?action=redirect&label=DigitalHouses%20SMB` возвращает 307 на `/?error=Not Valid&trace=unpacking idp - invalid character ...`. Поэтому HTTP доступность нельзя считать login acceptance.
- Корень первичной ошибки найден по исходникам установленного Filestash `76238d7fc8a090433ee0ea5976b14a6e660f5419`: штатный `LoadConfig()` получает параметры middleware; `Initialise()` может вызвать `SaveConfig()` во время установки/генерации `general.secret_key` **до** повторной инициализации производного ключа. Полученное шифрование не расшифровывается при следующем старте, и JSON-unmarshal IDP падает на непрозрачной строке.
- Исправление в №80: `dh-filestash-smb-config` создаёт 16-символьный `general.secret_key` до первого запуска Filestash, сохраняет его в приватном `config.json`, никогда не публикует. Повторный запуск сохраняет ключ и связанные параметры.
- Для уже сломанного экземпляра `--repair-broken-idp` допускает точечное восстановление **только** при наличии определённой выше live-ошибки, точных DigitalHouses SMB connections/middleware, корректного сохранённого secret_key и проверенном владельце файла. Перед переписыванием только двух middleware params создаётся исходная копия в root-owned `/var/backups/digitalhouses/filestash` (0700/0600). Остальная конфигурация сохраняется. После рестарта Filestash шифрует параметры правильным ключом.
- Для чужого backend, нового неизвестного типа IdP, отсутствия надёжного ключа или иной ошибки логина: `BLOCKED`, **не** удалять и не заменять весь `config.json`, не менять `CONFIG_ENCRYPT`, не выводить пароль/secret_key. При неподтверждённом исходе восстановления — остановить изменения и проверить read-only.
- После `Start Filestash` task №80 проверяет HTTP 200 и наличие полей `name="user"` и `name="password"` непосредственно у URL входа, без ввода пароля. Acceptance №81 делает ту же независимую read-only проверку. Отдельный клиентский тест SMB upload/download остаётся необходимым.
- На 30.10.2026 исправления находятся в исходниках Git; **живое применение и №81 не подтверждены**. В ходе удалённой диагностики попытка прочитать конфигурацию с авторизацией была отклонена защитой подключённого инструмента: не обходить отказ через другую командную оболочку/ключ/API. Перед допустимым запуском актуализировать pinned release защищённого worker штатным способом, затем применять `keep + import`, не `erase`.

## Запреты для будущих агентов

**Не просить пользователя повторно нажимать Run только потому, что один вызов инструмента не удался.** Сначала восстановить картину по журналам и безопасным штатным механизмам, включая исторический прямой запуск. Если конкретная попытка исполнить Ansible заблокирована платформой, **не обходить** этот отказ: честно показать границу и предложить доступный вариант через интерфейс. Не выполнять destructive-повтор, когда ошибка относится лишь к промежуточной настройке приложения.
