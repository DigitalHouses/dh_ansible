# ADR-0001 — Reusable resource operations, not per-object scripts

Статус: **Accepted**. Дата: 2026-10-05.

## Контекст

Legacy-проект показал анти-паттерн: на каждый атомарный шаг («создать пользователя», «создать снимок») создавались отдельные Bash/Python writer, preflight, independent verifier, test suite и командный wrapper, иногда с конкурирующими вариантами исполнения. Это увеличивало число источников истины, продолжительность внедрения и вероятность несовпадения guard/marker.

## Решение

1. Описание объектов — **данные**; общая Ansible role/module реализует **один контракт по типу ресурса**.
2. Операции выполняются по коллекции desired resources, со встроенным idempotent audit/diff/apply/verify. Пакетный вызов должен изолировать результаты отдельных ресурсов и корректно обрабатывать частичный успех.
3. Проверки пишутся **по поведению ресурса**, а не копируются для каждого пользователя или имени snapshot.
4. Вторую реализацию той же функции не заводим: расширяем проверяемый общий путь или заменяем его с явной миграцией и тестами.
5. Специальные скрипты допустимы только при доказанной невозможности использования штатного модуля/API (аппаратный bootstrap, recovery, нестандартное одноразовое действие). Исключение описывается в PR; такие скрипты не становятся теневой реализацией общего пути.
6. Дублирующие защитные маркеры и многократные страховочные writer запрещены. Для операций с неопределённым итогом применяется единый слой state reconciliation и запрет blind retry.

## Положительный пример

```yaml
truenas_users:
  - name: ha_user
    managed: true
    password_disabled: true
  - name: pve_user
    managed: true
    password_disabled: true
```

Эти элементы используют одну общую операцию. **Пример схематический:** реальные поля и серверные идентичности будут утверждены после live-аудита.

## Отвергнуто

- `create-ha-user.py`, `preflight-ha-user.py`, `verify-ha-user.py`, затем аналогичный комплект для `pve_user`;
- три варианта snapshot writer с разными маркерами и именами;
- уникальные shell wrappers как обязательная часть каждой обычной роли;
- «создать тест на каждый скрипт» вместо тестирования общего контракта ресурса.

## Контроль

На review: можно ли добавить очередную identity **только записью в inventory**? Если нет, реализация отклоняется, если только нет документированного реального исключения. Отдельные изменения ACL/снимков не объединяются в единую опасную «транзакцию» без анализа границ API.
