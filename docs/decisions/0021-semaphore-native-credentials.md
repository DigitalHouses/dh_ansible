# ADR-0021 — Site credentials: native Semaphore OSS storage

**Статус: архитектурное решение принято; №05/06 выпущены в `main` через PR #101, merge `b883ff85` (02.11.2026). Профильный CI 75/75 и изолированный API/storage E2E прошли. Live UI/PVE E2E ещё НЕ ПРИНЯТ; №07 и общий readiness gate не реализованы.**

### Пилот Semaphore 2.20.16-beta9 и совместимость с установленным №00

Первый принятый четырёхэтапный Bootstrap уже развернул **только №00**. Её root-owned seeder закреплён исходной Git-ревизией и разрешает для формы №05 только `Survey target=env`. Поэтому PR #101 **не пытается** обойти это ограничение ручной подменой seeder или изменением existing Task 00.

В пилоте №05 использует сохранённую Semaphore native Variable Group с названием `Empty`, уже привязанную ко всем шаблонам старого минимального Bootstrap. Это текущая совместимая **нативная** группа, не отдельное хранилище. В её `Secrets` значения API/PVE сохраняются как **type=var** и доступны №06 через механизм Semaphore 2.20 Ansible Vault encrypted extra-vars. Публичное название группы остаётся историческим до отдельного согласованного изменения seeder; не нужно создавать вторую секретную группу или дублировать PVE пароль в Key Store ради API.

**Survey формы №05 на этом экземпляре имеет target=env**, поэтому её входы идут через окружение Ansible controller (не argv), а сохранение происходит стандартным Ansible `ansible.builtin.uri` без собственного Python. Полная схема Beta `Survey target=var` будет возможна после штатного обновления закреплённого seeder в отдельной версии. Это **не скрытая миграция** и не уже принятый E2E.

Для чистого PVE mandatory credential начальной стадии — только `root@pam` пароль. №06 проверяет host-root TLS trust, HTTPS ticket и read-only `/nodes`. Остальные GitHub/MQTT/Cloudflare до своего commissioning — `NOT_APPLICABLE`. Общая глобальная политика строгого gate остаётся требованием для следующего этапа разработки.


Решение для новых объектов; существующие site/credentials не изменять автоматически.

## Решение

Каждый дом = собственный проект Semaphore. **Единственное рабочее хранилище
credentials объекта — штатные средства данного проекта Semaphore OSS.**
Не создавать обязательный plaintext credential store на runner, отдельный
site Vault в Git или собственный Secret Manager для текущих credentials.

- **Key Store → Local**: SSH keys, Git authentication, логины/пароли
  административного подключения, sudo/become и Ansible Vault passwords.
- **Variable Groups → Secrets**: переиспользуемые секреты приложений
  и API (MQTT, Home Assistant, Cloudflare и прочие), согласно
  поддерживаемой версии Semaphore и назначению потребляющего шаблона.
- **Secret Survey**: только одноразовая защищённая *передача значений* в задачу
  №05, не долговременное хранилище. Сохранение — через документированный
  API Key Store / Variable Groups, без вывода значений и CLI arguments.
- **Ansible Vault**: поддерживается для зашифрованных проектных данных,
  если необходимо. **Не является обязательным вторым хранилищем всех
  введённых credentials**, не должен дублировать Semaphore.

## Операторский UX

**05 · Obtain Credentials (одна задача на весь объект)**:
форма со скрытыми полями для всех используемых данным site credentials.
Администратор вводит всё необходимое **сразу**, одним запуском. Пустые
поля не стирают сохранённые значения. **Все поля ввода секретов должны
быть необязательными даже на первичной форме:** отсутствующие values
выявляет №06. В повторном запуске №05 можно ввести только один
неправильный пароль; остальные credentials сохраняются без изменений.
Форма показывает только безопасные metadata/status (`NOT_CONFIGURED`,
`STORED`, `CHECK_FAILED`), **никогда не подставляет старый секрет
как default**. Пустое значение = `KEEP`, а удаление должно быть отдельной
явной операцией с подтверждением; замена применяется лишь к указанному
credential, с сохранением остальных Key Store/Variable Group entries.
Для составных credentials (login+password) проверять целостность
вводимых полей и обновлять пару согласованно. Новое значение
не считается корректным, пока №06 не подтвердит реальную
аутентификацию. Изменение существующего секрета
должно быть явным, с правами администратора, по аналогии со штатным
Key Store Override. После записи проверить созданные идентификаторы и
привязки, но **не** печатать, возвращать в API-ответе или журналировать
значения секретов. Важно: заранее проверить на установленной версии
Semaphore, что все поля Secret Survey и операции API на самом деле
поддерживают этот контракт.

**Принятое решение о доверии и правах:** Semaphore и Ansible внутри
выделенного site runner LXC принадлежат **одному доверенному
административному контуру объекта**. Авторизованным Ansible playbooks
разрешён административный доступ к **своему проекту Semaphore** через
штатный localhost API, включая Key Store и Variable Groups. №05
использует тот же доступ для создания/обновления credentials.
Не создавать отдельный privilege broker, ограничивающий сервис,
API-токен на каждую задачу, root worker или собственный Secret Manager.

Это сознательно означает, что **любой доверенный playbook внутри
данного административного контура технически может менять все
credentials проекта**. Не выдавать этот принцип за least-privilege
изоляцию между задачами: граница безопасности — **объект/site runner**,
а не номер задачи. Ограничения между объектами сохраняются; доступ
одного site не должен охватывать проекты/credentials другого.
Право менять credentials Semaphore не означает автоматического root
доступа на PVE или других managed targets: их авторизация отдельно
комиссионируется штатными Ansible SSH/`become` средствами.

Для локального API использовать существующий официальный механизм
авторизации Semaphore; credential доступа хранить защищённо на runner,
не в Git, логах или аргументах командной строки. Защита OS filesystem,
аудит задачи и резервное восстановление Semaphore остаются обязательными.

**06 · Check Credentials (вторая универсальная задача)**:
читает сохранённые проектные credentials штатным способом, безопасно
проверяет **весь обязательный комплект** данного объекта (не только
credentials конкретной задачи), проверяет фактическую авторизацию и
необходимые привилегии. Проверки независимы и агрегируют **все ошибки**
без остановки на первой. Результат — перечень name/target/status/reason/
next action и итог `READY` или `BLOCKED`, без раскрытия секретов.
Коды: `PASS`, `MISSING`, `AUTH_FAILED`, `INSUFFICIENT_PRIVILEGES`,
`UNREACHABLE`, `UNVERIFIED`, `MISCONFIGURED`, `NOT_APPLICABLE`.
Не считать отсутствие связи доказательством неправильного пароля.

**Каждая обычная Ansible задача** вызывает тот же общий read-only
credential check в `pre_tasks` **текущего запуска** до изменения
инфраструктуры. Все обязательные credentials должны быть исправны;
неисправный MQTT-пароль может блокировать развёртывание PVE — это
сознательная строгая site policy владельца. Никаких исключений для
сервисов, не связанных с конкретным playbook. Исключение из readiness
gate: Bootstrap, 05 Obtain, 06 Check и санкционированное recovery,
иначе исправление credentials станет невозможным.

Семафор сохраняет историю успеха/ошибок задач, но **старый SUCCESS
не является бессрочным флагом разрешения**. При каждом новом Deploy
выполняется свежий Check внутри того же Ansible запуска. Отдельный
flag store и платный Semaphore Workflow не нужны.

## Автоматическое создание приватного репозитория нового объекта

**Нормативная схема:** один reusable репозиторий исходного Ansible-кода
`DigitalHouses/dh_ansible` + отдельный **приватный GitHub репозиторий
на каждый site** для его inventory, manifest, аппаратной спецификации,
описания HAOS и site-specific конфигурации. Пример рекомендуемого имени:
`DigitalHouses/site-serzhan-lab` (имя — соглашение проекта, не стандарт
GitHub). Пароли, токены и приватные SSH-ключи **не коммитить** в него:
рабочие credentials остаются только в Semaphore.

**Bootstrap остаётся минимальным**: Debian LXC, Ansible + Semaphore
и **только №00**. Он не создаёт private Git repository, потому что не
получает полномочий GitHub; №00 загружает каталог из публичного
`dh_ansible` без доступа к private site repo.

**Строгий порядок по решению владельца:**
1. Bootstrap создаёт только №00; №00 загружает каталог.
2. **№05 Obtain Credentials** принимает и сохраняет **все** credentials
   объекта, включая авторизованный GitHub credential с разрешением
   на первичное создание repo. №05 **не создаёт** репозиторий.
3. **№06 Check Credentials** проверяет весь обязательный набор, включая
   действительность GitHub credential и доступные для read-only проверки
   свидетельства полномочий. Без создания репозитория нельзя обещать,
   что фактическое разрешение на создание уже доказано; такой отказ
   корректно диагностирует сама №07.
4. **№07 Provision Site Repository** выполняется только после успешного
   *свежего* общего check. Если repo отсутствует — создаёт
   **`private: true`** штатным GitHub REST API
   `POST /orgs/{org}/repos` либо из version-controlled template
   `POST /repos/{template_owner}/{template_repo}/generate`.
   Если repo существует — выполняет безопасный `adopt` только после
   проверки владельца, приватности, identity/site_id и структуры;
   **никаких force push, wipe, implicit overwrite**.
   Проверяет результат через API, сохраняет URL в несекретных параметрах
   проекта, подключает repository к Semaphore и применяет отдельную
   read-only identity для обычной работы.
5. При исправлении только одного credential администратор повторяет
   №05 с одним заполненным полем, затем №06. **№07 не запускается
   автоматически из №05**, существующий repo не меняется.

**Привилегии:** право создать репозиторий в `DigitalHouses` требует
авторизованной GitHub identity с repository creation permissions
(организация может ограничивать создание). Эти полномочия нужны
**только при initial provisioning**. Не сохранять организационный
admin PAT в Key Store домашнего runner для повседневных операций.
Для дальнейшего чтения Git использовать отдельный read-only deploy key
только этого репозитория (или равноограниченную GitHub App identity),
хранимый в штатном Key Store Semaphore и привязанный к конкретному
repository. Создание репозитория использует временно авторизованное в №05
GitHub разрешение; оно не должно оставаться постоянным
административным доступом домашнего runner. После успешного №07
повседневные задачи используют только site-scoped read-only identity.

**Site template:** минимальный README и структура inventory/config,
без секретов, без перезаписи существующей HA-конфигурации. Код общих
ролей остаётся в `dh_ansible`, а site repo содержит лишь данные
объекта. Не копировать `dh_ansible_fleet_detail` целиком и не
переносить credentials из соседних объектов.

**Повтор №05:** при исправлении одного MQTT-пароля существующий
репозиторий **не трогается**. Проверка или adopt существующего repo
относится к отдельной повторно запускаемой №07.
Отсутствие repository-creation прав после первого provision
не должно блокировать обновление сохранённых site credentials.

**Реальное ограничение установленного seeder:** для №05 он принимает пять необязательных полей Survey только с `target=env`; новые `target=var` в схему каталога пока не допускаются. Защищённая передача Variable Group Secrets `type=var` в Ansible уже поддерживается Semaphore 2.20 Beta. Изменение формата формы №05 требует отдельного обновления доверенного seeder, а не ручной подмены на работающем runner.
Одна форма с частичным вводом должна быть реализована штатными
Survey fields, а не отдельным self-hosted password portal.

**Приёмка:** №05 и №06 не создают GitHub repo;
№07 создаёт новую репу `private=true` ровно один раз,
второй запуск делает `adopt`, раздельные дома не видят private
data друг друга; read-only ключ не может создавать репозитории.
Тест частичного ввода: после двух неправильных credentials
№06 сообщает оба, а повтор №05 с одним исправлением не
изменяет остальные; второй №06 сообщает только оставшуюся ошибку.
Reboot и восстановление БД Semaphore проверяются отдельно.

## Хранение, безопасность, восстановление

- Никаких secrets в коде, plaintext Git, логах, выводах диагностики,
  CLI argv, именах файлов и обычных Ansible facts; `no_log` на операциях
  с секретами, отдельно сформированный безопасный отчёт.
- №05 запускается только уполномоченным администратором объекта.
  Все доверенные Ansible playbooks этого site runner находятся в одном
  административном контуре с Semaphore и имеют полномочия управления
  **своим** проектом. Не притворяться, что задачи изолированы по правам,
  если используют единую административную identity; не распространять
  полномочия на другие site.
- Защищённая резервная копия **базы Semaphore + отдельно защищённая
  копия `access_key_encryption`** и проверенное восстановление.
  Потеря ключа делает сохранённые в БД secrets непригодными.
- До удаления старого CT и миграции №05/06 провести на `serzhan-lab`
  контрактный тест supported API и роли, тест двух неверных credentials,
  reboot и восстановление из резервной копии. Не переносить автоматически
  credentials других объектов.

## Migration / supersedes

Этот ADR **заменяет целевую схему** обязательного
`site_vault_v1` из раннего прототипа (2026-11-01). В `main` до публикации PR остаются прежние №05 GitHub/№06 Fleet Vault, а в draft PR #101 новые 05/06 ещё не прошли живую приёмку. Исторический `fleet_credentials` сохраняется для старых задач; он не источник новых credentials.
Не заявлять, что система внедрена, пока весь путь 05 → 06 → обычная
задача не принят E2E. Старую функциональность сохранять до проверенного
перевода, не удалять credentials без резервной копии.
