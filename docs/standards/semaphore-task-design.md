# Стандарт проектирования задач Semaphore · DigitalHouses / Ansible-2

**Статус:** обязательный инженерный стандарт для новых задач и значимых изменений существующих.
**Область:** публичный `dh_ansible`, приватный `dh_ansible_fleet_detail`, site runner, PVE и внешние API.
**Приоритет:** применять совместно с [инженерными принципами](../engineering-principles.md) (P01–P15), [ADR-0018](../decisions/0018-semaphore-self-service-and-cloudflare.md) и [ADR-0019](../decisions/0019-reusable-semaphore-task-dependencies.md). При расхождении с утверждённым принципом сначала пересмотреть решение, не делать скрытое исключение.

## 1. Основной контракт: инженер нажимает одну кнопку

- **Одна пользовательская операция = одна видимая задача Semaphore.** Инженер не обязан знать порядок запуска других задач и вручную доставлять зависимости. Нумерация 00/10/20/... — порядок представления в UI, **не** зависимости исполнения.
- Одна задача сама выполняет разрешённую последовательность: `resolve site-data → audit → plan → approved apply → verify → result`. Необязательные этапы пропускаются явно, а не притворяются выполненными.
- **Переиспользуемый этап — роль/набор Ansible tasks или фиксированная capability worker, а не дополнительная кнопка.** Переиспользование кода предпочтительнее создания нового шаблона Semaphore.
- `audit` и `plan` не изменяют инфраструктуру; `apply` допускается только при выполненных политике и предусловиях; `verify` независимо проверяет живой результат. Ansible `--check` не заменяет реальный plan.
- Если общий prerequisite не подготовлен, итог **BLOCKED с точной причиной**, до любой записи. Не требовать от инженера запуска «сначала 05/50, потом 80».
- Не выдавать `SUCCESS` операции установки за успех, когда только проверен план. Отчёты различают `AUDIT_PASS`, `PLAN_ONLY`, `APPLY_CHANGED`, `APPLY_UNCHANGED`, `VERIFY_PASS`, `BLOCKED` и `UNKNOWN`.

## 2. Выбор механизма по функциональному назначению

| Класс операции | Рекомендуемый механизм | Когда root-worker обязателен | Примеры действующих задач |
| --- | --- | --- | --- |
| Локальный smoke, состояние обычного сервиса, безопасный диагностический read-only | Прямой Semaphore playbook → переиспользуемые Ansible roles/modules | Только если конкретная диагностика требует защищённых ресурсов | **20**, **30** |
| Read-only аудит, которому нужны root-файлы, приватные SSH-ключи или API-токены | Semaphore → nonce request → фиксированный root-worker → независимый audit → status | Да; секреты остаются у доверенного исполнителя | **50** |
| Установка/обновление локального привилегированного сервиса | Semaphore → nonce → root-worker; Ansible apply/verify внутри | Да | **40** |
| Создание VM/LXC, PCI passthrough, конфигурация PVE и гостевой ОС | Декларативная роль + `audit/plan` → строго ограниченный worker → PVE API/проверенный SSH → `verify` | Да, если затрагивается PVE/устройства | **60** как действующий пример LXC; **80** пока только план и не готова к apply |
| Облачные API, Cloudflare Tunnel, Access, mTLS | План и проверка защиты → root-worker со scoped credential → readback удалённого API | Да | **10**, **70** |
| Управление самим каталогом Semaphore | Публичный `catalog/semaphore-tasks.json` → фиксированный root-worker → официальный localhost HTTPS Semaphore API | Да, поскольку управляющий API-токен root-only | **00** |
| Много независимых жизненных циклов, требующих явных границ утверждения/отката | В будущем нативный Workflow со звеньями, построенными из утверждённых пользовательских задач или reusable этапов | По требованиям каждого звена | **Целевая архитектура; не считать внедрённой** |

**Правило выбора:** сначала штатный модуль/коллекция Ansible → общая роль → существующий доверенный worker. Новый Bash/Python-исполнитель создавать только при доказанном отсутствии подходящего механизма, аппаратном/bootstrap-ограничении или независимой диагностике. Отдельный worker на каждую мелкую операцию — архитектурный дефект.

Работающий пример композиции — [`request-netalertx-install.yml`](../../playbooks/request-netalertx-install.yml) и [`netalertx-deploy-request.sh`](../../bootstrap/netalertx-deploy-request.sh). Но это **образец разграничения привилегий**, не гарантия, что каждая его деталь уже соответствует всем новым требованиям.

## 3. Какие сущности создаются при новой функциональности

| Сущность | Когда создавать | Когда не создавать |
| --- | --- | --- |
| **Ansible role / tasks** | Появился новый переиспользуемый тип ресурса или этап | Только ради нового дома, одной VM или другой комбинации site data |
| **Semaphore template** | Появилась самостоятельная осмысленная **операторская цель**, которую нужно запускать отдельно | Чтобы вручную связать prerequisites `sync → audit → plan` одной операции |
| **Root worker** | Доверенной привилегированной операции нет в существующих возможностях | Для каждого audit/assert, если их может исполнить существующий механизм |
| **Fleet inventory entry** | Новый дом, ресурс, параметр или approval | Чтобы дублировать код/секреты в публичном репозитории |
| **Workflow** | Несколько самостоятельных этапов с утверждениями, checkpoints, независимыми retry/recovery | Только чтобы запустить несколько ролей Ansible последовательно |

Шаблон, зарегистрированный в `catalog/semaphore-tasks.json`, при обновлении **менять на месте**, сохраняя ID и историю. Удаление управляемых/старых шаблонов — отдельная процедура с защитой истории. Задача `00` не может исчезнуть в результате синхронизации. Никогда не вводить скрытый `autorun` для инфраструктурных изменений.

## 4. Source of truth, Fleet Detail и секреты

| Источник | Содержимое | Допустимое место использования |
| --- | --- | --- |
| **`dh_ansible` (PUBLIC)** | Код, роли, playbooks, каталог, документация, синтетические тесты | Semaphore клонирует public Git |
| **`dh_ansible_fleet_detail` (PRIVATE)** | `inventories/<site>/`, декларативные approvals, encrypted Fleet Vault | Только доверенный owner-authorized provider; site-scoped данные передаются в runner |
| **Site inventory на runner** | Локальная материализация нужных YAML: `/var/lib/ansible/site-data/<site>/` | Semaphore читает файлы `root:semaphore 0640`; это **не** source of truth |
| **Runtime / escrow secrets** | Права PVE/Cloudflare/SSH и ограниченные служебные материалы | Под контролем root-worker и утверждённой модели Vault/escrow; не в общем environment Semaphore |

**Принципиальное различие:** обновление **каталога** задач (00) не обновляет **Fleet Detail**. Загрузка публичного Git при запуске Ansible не обновляет приватный inventory. Успех `include_vars` подтверждает доступ к файлу, **не свежесть данных**.

**Сейчас реализовано:** owner-authorized [`semaphore-host-install.py`](../../bootstrap/semaphore-host-install.py) получает private Fleet по проверенному commit, передаёт только site YAML через `pct push`, проверяет хеши и устанавливает `root:semaphore 0640`; GitHub-вход владельца временный. Задача 80 сейчас использует [`site_inventory_prepare`](../../roles/site_inventory_prepare/tasks/main.yml), но эта роль **проверяет локальные файлы, а не скачивает отсутствующие или устаревшие**. Без специально настроенного источника runtime secrets её вызов `fleet_secrets` также не является рабочим способом получить PVE token.

**Целевой механизм для one-click новых задач (не внедрён):** общий `site_data` provider, доступный из доверенной privileged boundary, должен:
1. Определить текущий `site.id` из проверенной локальной identity, проверить разрешённый source/commit и доступный credential.
2. Получить **только** нужные данные `inventories/<site>/` из зафиксированной проверяемой ревизии; не открывать всему runner private Git, чужие sites или Fleet Vault.
3. Сверить текущее состояние и SHA256, поддержать новую редакцию уже существующих файлов через проверенный diff; не считать любое отличие взломом и не молча стирать ручные изменения.
4. После проверки выполнить atomic staging/replace для разрешённых файлов с владельцем `root:semaphore 0640`; не удалять неупомянутые ресурсы; подтвердить хеши после изменения.
5. Вернуть `CHANGED/UNCHANGED/BLOCKED` с ревизией и безопасной диагностикой. Если источника/credentials нет, **отказ до PVE API/PCI изменений**, без фальшивого успеха.

**Нельзя** ради «одной кнопки» помещать GitHub PAT/owner OAuth/master Vault/password в Semaphore environment или сохранять полную private Fleet копию в runner. Provider должен быть отдельно принят и проверен на site-isolation.

## 5. Фиксированный root-worker: стандарт безопасного вызова

Типовая цепочка:

`Semaphore (unprivileged) → request {fixed action, UUID, site} → systemd.path/oneshot root-worker → pinned/verified operation → atomic status {UUID, result} → Semaphore verify`.

Обязательные свойства:

- Узкая грамматика запросов; **никаких свободных путей, URL, shell-команд, arbitrary playbook или пользовательских extra-vars**, управляющих scope.
- Проверка hostname/site identity, владельца/режима/symlink запроса и доступного worker. UUID связывает ответ строго с текущим запуском; повтор старого результата недопустим.
- Singleton lock (или иной доказанный метод предотвращения конкуренции), bounded timeout, отдельный root-only журнал; в UI только безопасный результат без токенов, паролей и приватных данных.
- Worker фиксирует доверенный исходный код: **pin/verification Git commit** и контроль исполнения ожидаемого playbook. Не считать `git clone main` сам по себе immutable; у действующего NetAlertX-worker эта часть требует укрепления.
- При неизвестном результате write — `UNKNOWN → stop writes → read-only reconcile`, без слепого повторения. При смене PCI, сетей, ACL и дисков — независимая проверка условий и явная авторизация конкретного изменения.
- Передавать в UI `PASS` только после проверки postconditions, а не только нулевого exit code worker.

## 6. Workflow: целевая модель, не подмена Ansible

Workflow — граф крупных операторских этапов, а не новая база состояний и не последовательность кликов инженера.

Пример **будущего** workflow установки VM:

`site-data → audit PVE/PCI → plan → create VM stopped → OS acceptance → explicit PCI handoff approval → attach GPU/SATA → verify → report`.

Внутри каждого этапа остаются те же общие Ansible roles и проверенные root-workers. Workflow отвечает только за зависимости, разрешённые переходы, статус и возобновление после отказа; **не** дублирует вычисление конфигурации VM. Блокировка любого обязательного звена не должна запускать следующее; запрет destructive actions действует и при автоматической оркестрации.

Пока нативный Workflow не принят E2E, одна Semaphore-задача объединяет этапы посредством `include_role` / `import_tasks` / fixed worker. **Не добавлять новые UI templates исключительно для искусственной цепочки.** Нельзя обещать пользователю автоматический workflow, если фактически работает только последовательный playbook.

## 7. Обязательный процесс создания или изменения задачи

1. **Назначение:** определить один результат для инженера, класс операции из таблицы §2, риск routine/sensitive/destructive и является ли новая UI-кнопка действительно необходимой.
2. **Источники:** перечислить требуемые site YAML, Vault/runtime secrets, API principals, PVE host access, versions/commits; до написания задачи проверить, что они **реально доступны в среде исполнения**.
3. **Reuse:** найти существующий playbook/role/worker и точку встраивания. Не создавать второй способ делать ту же инфраструктурную операцию.
4. **Контракт:** описать входной desired state, idempotency, ownership/adopt, fail-closed gates, ограничения существующих ресурсов, точные изменения и условия acceptance.
5. **Security:** проверка site slug, локального runner, pinned SSH host/TLS identity; root-worker только когда нужен, никакого повышения полномочий Semaphore.
6. **Implementation:** код только в публичном репозитории, реальные параметры только в приватном Fleet; register/update в `catalog/semaphore-tasks.json` только если оправдан новый операторский шаблон.
7. **Testing:** CI syntax, unit/contract tests, secret-boundary scan, отсутствующие/неверные site data, отказ credentials, дрейф, нештатный повтор worker, idempotency; отдельный site read-only E2E перед `apply`.
8. **Real acceptance:** проверить фактический пользовательский запуск **одной кнопкой**, UUID/status и postconditions; повторный apply без изменений `changed=0`; задокументировать источник Fleet revision, outcome и ограничения.

**Запрет на релиз:** если задача требует файла, которого нет на runner, зависит от неустановленного worker или недоступных secrets, её нельзя считать готовой к one-click. Не исправлять это инструкцией инженеру «сначала запусти соседнюю задачу». Исправляется общий prerequisite или задача честно остаётся `BLOCKED / NOT_COMMISSIONED`.

## 8. Реестр реализованных точек входа (обновлять вместе с каталогом)

| Номер | Функциональный механизм | Нынешняя оценка |
| --- | --- | --- |
| **00** | Управление каталогом → root-worker + localhost Semaphore API | Действует; **не** обновляет Fleet Detail |
| **10** | Cloudflare connector → fixed-purpose root-worker | Действует по защищённому запросу |
| **20** | Простой Ansible smoke | Действует |
| **30** | Ansible read-only runner audit | Действует |
| **40** | Привилегированный локальный service install/pair → root-worker | Действует |
| **50** | Read-only PVE access audit → root-worker | Действует |
| **60** | NetAlertX plan + root-worker + guest provisioning/apply | Действует; пример one-click |
| **70** | HAOS mTLS preflight + approved root-worker | Действует |
| **80** | Media VM read-only plan + `site_inventory_prepare` + `fleet_secrets` | **Не готова к one-click**: нет гарантированной доставки `media_vm.yml` и источника secrets; создание VM не реализовано |

**Этот реестр описывает наблюдаемую реализацию на дату написания; не служит автоматическим разрешением на запуск write-операций.** После изменения каталога или реализации обязан обновляться как часть того же PR.

## 9. Антипаттерны, обнаруженные при задаче 80

- Добавить новую переменную в private Git и предполагать, что она сама появится в локальном runner inventory.
- Подключить роль `fleet_secrets` без реально настроенного источника secrets в контексте исполняющего пользователя.
- Сделать отдельную задачу «обновить inventory», которую инженер должен помнить и вручную вызывать перед развёртыванием.
- Объявить read-only «аудит» готовой установкой или считать выключение прежних гостей разрешением на несанкционированный PCI handoff.
- Выдать отсутствие SSH/private Git credential за проблему с `git pull` и решить её копированием глобального токена в Semaphore.
- Плодить отдельные PVE/Cloudflare/NetAlertX worker-script'ы для каждого экземпляра ресурса.

**Архитектурный результат:** единый код по типу операции; объект отличается данными; инженер нажимает одну кнопку; доступ и права минимальны; каждый этап честно сообщает о том, что выполнено, а что ещё не реализовано.
