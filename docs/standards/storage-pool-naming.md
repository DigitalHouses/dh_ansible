# Стандарт именования ZFS-пулов · DigitalHouses / Ansible-2

**Статус:** обязательный стандарт для всех новых управляемых Ansible ZFS-пулов.
**Область:** все объекты Fleet, PVE, Linux VM/LXC и другие поддерживаемые ZFS-хосты.
**Принят:** 2026-10-27.

## Каноническое имя

**Имя нового ZFS-пула данных — `<owner>-pool`.** `owner` — канонический slug владельца объекта из приватного Fleet inventory (`site.owner_slug`), а не полный `site.id`, адрес, назначение сервера, service name или произвольная подстрока имени.

Например, для `site.owner_slug=serzhan` и `site.id=serzhan-home` имя нового пула: **`serzhan-pool`**, не `serzhan-home-pool`.

Обязательные требования:
- Имя вычисляется из объявленного `site.owner_slug` или утверждённого поля владельца в Fleet SoT. **Не** получать его обрезанием `site.id` и не вшивать имена владельцев в роли.
- Общее правило распространяется на любой *новый* создаваемый Ansible ZFS-пул данных, независимо от его назначения (медиа, backup, документы и т. д.) и типа узла.
- Названия dataset и каталогов должны выводиться из объявленного фактического `storage.pool_name`, а не собираться отдельно из `site.id`. Например: `serzhan-pool/media`, `serzhan-pool/backups`, `/serzhan-pool/digitalhouses`.
- Не добавлять к имени пула `-home`, `-office`, `-media`, ID гостя или объектные суффиксы. При конфликте имён на одном хосте — `BLOCKED`, требуется отдельно согласованное исключение в приватном Fleet inventory, **никакого автоматического переименования/генерации суффикса**.
- Валидация Ansible сверяет имя **нового** пула с `site.owner_slug ~ '-pool'`; в случае утверждённого исключения проверяется явно объявленный namespace.
- Повторный запуск должен быть идемпотентным (`changed=0`) и не пересоздавать пул.

## Существующие пулы и режим import

Это правило **не разрешает автоматическое переименование существующих пулов**. Например, работающий `serzhan-home-pool` — legacy-имя и остаётся без изменений до отдельно принятого плана миграции. Не переименовывать его и не менять `mountpoint`, datasets, backup/NFS/SMB пути или зависимости приложений в рамках обычного `keep + import`.

- `import`: безопасно обнаружить и подключить существующий пул под его **фактическим именем** из проверенного inventory, сохранив данные и существующие связи. Не принимать желаемое новое имя за команду переименования.
- `erase`/создание нового пула: только после отдельного подтверждения операции и всех защитных проверок применять каноническое `<owner>-pool`.
- Переход legacy-пула к каноническому имени допускается только как **отдельная операция**: audit всех mountpoints/datasets, ссылок в VM, Samba/NFS/Plex/Arr, backup, SSH/автоматизациях; plan → явное разрешение → apply с recovery plan → независимый verify. Само принятие стандарта не является таким разрешением.
- Если текущий код не различает `import` legacy и создание нового пула, **блокировать production apply** до исправления этой логики. Не обходить защитные проверки ради соответствия имени.

## Приёмка

1. Новый пул имеет имя `<owner>-pool` и подтверждён владельцем из Fleet SoT.
2. При `import` сохранились фактическое имя, GUID, данные и mountpoints существующего пула.
3. Dataset/пути сервисов следуют `storage.pool_name`; отсутствует неявная зависимость от `site.id ~ '-pool'`.
4. Проверена повторная установка без неожиданных изменений; существующие пулы не затронуты.
